Shared Stats Models

ESPN, Fox and Paramount each re-invent the same five entities — team, competitor, contest, stat row, status — in mutually incompatible shapes. The evidence below is drawn from the current source, and it already contains three implementations of one function that disagree on their output.

What the code already says

The argument was made in-repo before it was made here

Paramount's football models carry a header comment that states the thesis of this document exactly. It was written to justify a helper that fixed the problem inside one service of one client:

footballFormat.bs:1–7

"Every model was growing its own int/number/ordinal/record/playerName, which is both duplication and a place for the four to quietly disagree — a rank rendering as 1st in one card and 1th in another is exactly the kind of drift this prevents."

The same drift in name formatting

Fmt.playerName exists and formats "G. Minshew". Three Paramount cards ignore it and re-derive the same initial inline from firstName/lastName:

  • judgesScoresCard.bs:203
  • taleOfTheTapeCard.bs:231
  • fightCard.bs:412

A helper that exists but isn't reachable from where the work happens gets reimplemented. That's a structural problem, not a discipline problem.

One lifecycle, three encodings

Status is the clearest case for a shared type

  • Every client models the same three-state contest lifecycle.
  • No two agree on the representation, and one uses integers.
  • No value can cross a client boundary without translation.

The two Paramount enums are near-duplicates of each other; the NFL file's own header admits it — "Mirrors src-sdk/paramount/server/StatsService/enums/enums.bs (FightStatus)".

Both ship a hand-rolled normalize(), each accepting an overlapping-but-unequal set of raw strings.

The same entity, five vocabularies

Field-name divergence across clients

  • A team is the most-read entity in all three clients.
  • No two definitions match — not even within a single client.
  • Fox alone carries two incompatible team shapes, depending on which service produced it.

The last row is the expensive one — away/home, team1/team2 and left/right are three different questions: semantic, feed-ordered, positional. Code that assumes one while reading another silently renders the wrong side.

  • Three take teams as object and call .DoesExist() on it directly.
  • The fourth takes dynamic and guards.
  • Whether a missing team crashes depends on which card the user is looking at.

A guard that cannot fire

This line reads as a null-check but never rejects anything:

BetsDataModel.brs:61 · latent 
if athletes = invalid or (event?.competitions = invalid and event?.competitions.Count() = 0) then return invalid
  • and should be or. As written, the competitions guard is dead code and parseMatchTable always returns a table.
  • It hasn't crashed only because of short-circuit evaluation — when the left side is true, the right side (which dereferences a value just proven possibly-invalid) never runs.
